## 影响力框架：三层 x 四种机制

```mermaid
graph TB
    subgraph TIERS["三个影响力层级"]
        direction LR
        T1["个体 (Individual)<br/>──────<br/>提升一个人的技能<br/>一对一互动"]
        T2["群体 (Group)<br/>──────<br/>同时影响多人<br/>新技能或新方法"]
        T3["催化剂 (Catalyst)<br/>──────<br/>超越你直接的影响<br/>建立框架和社区结构<br/>即使你离开<br/>正向影响继续"]
    end

    T1 --> T2 --> T3

    style TIERS fill:#f8f9fa,stroke:#333
```

### 影响力矩阵（原书 Table 8-1）

| | 个体 (Individual) | 群体 (Group) | 催化剂 (Catalyst) |
|---|---|---|---|
| **建议** | 指导、分享知识、反馈 | 技术讲座、文档、文章 | 建立指导计划、技术活动 |
| **教学** | 代码审查、设计审查、教练、结对、影子 | 课程、codelab | 入职课程体系、教别人去教 |
| **护栏** | 代码审查、变更审查、设计审查 | 流程、linter、代码风格指南 | 框架、文化变革 |
| **机会** | 委派、赞助、鼓励、持续支持 | 分享舞台、赋能团队 | 创造机会文化、看着你赞助的新人改变世界 |

> **不要跳过"小"的。** 即使最改变世界的技术领导者仍然在做一对一的指导。个体和群体层级的工作先做好，只有在需求明确时才扩展到催化剂层级。太多框架和程序会让组织不堪重负。

## 二、教学（Teaching）

教学 vs 建议的区别：**建议是告诉，教学是让对方理解并内化。**

### 个体教学

```mermaid
graph TB
    TEACH_IND["个体教学"]

    TEACH_IND --> TI1["解锁话题<br/>──────<br/>最好的课让你感觉<br/>'我掌握了以前不会的东西'<br/>这是解锁 (unlocking)<br/><br/>教学要有目标：<br/>• 系统概览？→ 他们应该能<br/>  在白板上画出来<br/>• 走读代码库？→ 他们应该能<br/>  发第一个 PR<br/>• 展示工具？→ 描述3-5个场景<br/>  他们应该能独立处理"]

    TEACH_IND --> TI2["协作教学谱系<br/>──────<br/>影子 (Shadowing)：你做，他们看<br/>→ 做榜样、展示高标准<br/><br/>结对 (Pairing)：一起做<br/>→ 你带领或他们带领或平等<br/>可以是编程、写文档、白板<br/><br/>反向影子：他们做，你看<br/>→ 学习效果最好<br/>给实时反馈<br/>= 也是一种护栏"]

    TEACH_IND --> TI3["代码和设计审查作为教学<br/>──────<br/>资深的人审查可以极大提升信心<br/>⚠️ 也可以摧毁信心<br/>居高临下/武断/看不懂的评论<br/>= 让人痛苦<br/><br/>教学式审查原则：<br/>• 理解审查任务<br/>  （新人学习？还是安全检查？）<br/>• 解释为什么，不只是什么<br/>  不要只说'用 unique_ptr'<br/>  说明为什么<br/>• 给出改进的例子<br/>  不要只说'让这段更清晰'<br/>• 标注什么重要什么是偏好<br/>  安全漏洞 vs 拼写习惯<br/>• 选择战场<br/>  先看高层方向，再看细节<br/>  如果方向错了<br/>  别留100条技术建议<br/>• 如果你同意就说'yes'<br/>  明确说你没异议<br/>  主动表扬好的部分<br/>• 记住你可能吓到对方<br/>  友善、人性化<br/>  大量反馈时考虑<br/>  约会议而非写评论"]

    style TEACH_IND fill:#f3e8fd,stroke:#9334e6
```

## 三、护栏（Guardrails）

护栏就像悬崖小路上的栏杆——**不是用来靠着的，但当你需要时它能救命。** 护栏鼓励自主、探索和创新。当行进安全时，所有人都走得更快。

### 个体护栏

```mermaid
graph TB
    IND_GUARD["个体护栏"]

    IND_GUARD --> IG1["代码/设计/变更审查<br/>──────<br/>知道工作会被审查<br/>→ 工程师更有信心独立工作<br/>不会造成宕机或<br/>建了几个月走不通的架构<br/><br/>好护栏的审查要点：<br/>• 这个工作应该存在吗？<br/>• 它解决了问题吗？<br/>• 它怎么处理故障？<br/>• 它可理解吗？<br/>• 它符合大局吗？<br/>• 对的人知道吗？<br/><br/>⚠️ 不要橡皮图章<br/>认真读每一行<br/>好护栏 ≠ 武断的守门人<br/>你和被审查的人在同一边"]

    IND_GUARD --> IG2["项目护栏<br/>──────<br/>当有人做延伸性项目<br/>有一个做过类似事的人<br/>每周 check-in<br/>问有针对性的问题<br/><br/>作者的例子：<br/>Team Lead 每周问<br/>'你打算怎么平衡<br/>这两个冲突的业务优先级？'<br/>她当时没想到<br/>但问题帮她回到正轨<br/>如果她走近悬崖<br/>他准备好教练她<br/><br/>Lara Hogan 的建议：<br/>具体说明你能帮什么：<br/>'我可以审你的设计'<br/>'如果B三天没回<br/>给我发邮件，我来推'"]

    style IND_GUARD fill:#fce8e6,stroke:#ea4335
```

### 规模化护栏到群体

```mermaid
graph TB
    GROUP_GUARD["群体护栏"]

    GROUP_GUARD --> GG1["流程 (Processes)<br/>──────<br/>发布前检查清单：<br/>• 需要安全审批吗？<br/>• 给市场/客服多少提前量？<br/>• 用 feature flag 吗？<br/>• 有标准监控/事件/文档吗？<br/>• 需要通知其他团队吗？<br/><br/>流程的困境：<br/>不写 → 没人知道怎么做<br/>写了 → 被当法律条文抠字眼<br/>写得面面俱到 → 三环活页夹<br/>没人看<br/><br/>作者的 Process Preamble<br/>（流程前言模板）：<br/>'这些答案不会在所有情况<br/>都完美适用<br/>丢弃之前三思<br/>但如果不适合你的情况<br/>做有道理的事<br/>所有准则有时候都是错的'"]

    GROUP_GUARD --> GG4["催化剂：文化变革<br/>──────<br/>最强的护栏<br/>也是最难建立的<br/><br/>代码审查和写测试<br/>曾经不是标准！<br/>是有人坚持推动的<br/>要有耐心<br/>找盟友、赞助人<br/>用影子组织架构(ch2)<br/><br/>解决真实问题、选择战场<br/>提供支持、找盟友<br/>让正确做法成为最简单的做法"]
```

## 四、机会（Opportunity）

人通过**做**学到的，比通过教学、教练或建议学到的更多。每个项目或角色都是可见度、关系和简历的机会。

### 个体机会

```mermaid
graph TB
    IND_OPP["个体机会"]
```

### 关于晋升的重要提醒

> **别人被晋升到你的级别，不需要像现在的你一样强——他们只需要像你刚被晋升时一样强。** 如果你发现新晋升的人不如你，不要嘲讽标准降低了——想想是不是你成长了。
